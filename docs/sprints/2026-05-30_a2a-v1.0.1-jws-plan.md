## Item 3 — `signatures`-Property (JWS)

**Was:** AgentCard mit `signatures: [AgentCardSignature]` ausliefern. Pro Signatur: `protected` (base64url-JSON-encoded JWS-Header) + `signature` (base64url Ed25519-Signatur).

**Schema (aus `a2a.proto`):**
```protobuf
message AgentCard {
  …12 existing fields…
  repeated AgentCardSignature signatures = 13;
}
message AgentCardSignature {
  string protected = 1;  // base64url JWS header (alg, kid, typ)
  string signature = 2;  // base64url raw signature bytes
}
```

**Was wir verifiziert haben (30.05.) — Infrastruktur ist zu ~70% schon da:**
- `app/registry_keys.py` — `REGISTRY_KID = "moltrust-registry-2026-v1"`, `get_private_key()` für Ed25519
- `app/signature.py` — komplettes JCS + JWS-Toolkit: `canonicalize()` (RFC 8785 via `jcs` lib), `_b64url_encode()`, `sign_payload()`, `build_registry_jws()` mit JWS-Compact-Serialization
- `app/caep.py:205` — `/.well-known/registry-key.json` Endpoint mit JWK
- Public Key bereits unter `/var/www/html/.well-known/jwks.json` (4385 bytes, vorhanden seit 27.05.)
- `build_registry_jws()` wird bereits in main.py:1437 für trust-score response produktiv genutzt

**Was fehlt — der Delta:**
Compact JWS (existing) ist `<header>.<payload>.<sig>` als ein String. AgentCardSignature splitted das auf: `protected` (header_b64) + `signature` (sig_b64) als **separate Felder**, payload ist die AgentCard selbst (ohne `signatures`-Feld). Also nicht Compact-JWS, sondern **JWS-Detached-Signature-Style** über die AgentCard.

**Implementation in 6 Schritten:**
1. AgentCard laden, `signatures`-Feld entfernen
2. JCS-canonicalize die verbleibende Card → `payload_canonical_bytes`
3. Protected Header: `{"alg":"EdDSA","kid":"moltrust-registry-2026-v1","typ":"a2a-card+jws"}` → JCS + b64url → `protected_b64`
4. Signing input: `f"{protected_b64}.{_b64url(payload_canonical_bytes)}".encode()` (per RFC 7515)
5. Signature: `get_private_key().sign(signing_input)` → b64url → `signature_b64`
6. Card mit `signatures: [{"protected": protected_b64, "signature": signature_b64}]` zurückgeben

**Files:**
- `app/a2a_card_signer.py` — **neu, ~30 LOC** (nutzt 100% existierende Helpers aus `signature.py`)
- `app/main.py` — `_load_public_agent_card()` zu `_load_signed_public_agent_card()` umbauen, Caching beibehalten (Card-Content ist stabil → Signatur einmal beim ersten Load berechnen)
- `tests/test_a2a_card_signing.py` — **neu, ~40 LOC** (Round-Trip Verify mit `nacl.signing.VerifyKey` + Public Key aus `jwks.json`, Tamper-Detection)
- `requirements.txt` — **unverändert** (`jcs` ist schon drin, siehe `signature.py` Import)

**Aufwand:** **1.5–2h**, breakdown:
- 30 min Signer-Modul (mostly Glue-Code um existierende Helpers)
- 30 min main.py-Integration + Cache-Strategie
- 30 min Tests + JWK-basierte Verify-Roundtrip
- 30 min PR + Reviewer-Pass

**Server-Deploy:** **Ja** — Code-PR + `systemctl restart moltstack.service`. Static-File unverändert (Signatur ist Server-side-generated und in der HTTP-Response-Card).

**Risiko:**
- JCS-Implementierungs-Inkonsistenz mit upstream Reference-Implementations → **niedrig**: wir nutzen die etablierte `jcs` lib die schon im produktiven trust-score-Signing-Pfad läuft (CAEP)
- Key-Rotation für `kid: moltrust-registry-2026-v1` ist Jan 2027 geplant (per `registry_keys.py` Docstring) → Out-of-Scope, aber für Call erwähnenswert

**Strategischer Bonus:** Genau dieses Feature ist die natürliche Story für „MolTrust = signed Agent Identity". Andere Implementierer haben es noch nicht — und wir haben den ganzen Crypto-Stack bereits produktiv. Erste in Production mit JWS-Signatur = klare Positioning-Story für den Call.
