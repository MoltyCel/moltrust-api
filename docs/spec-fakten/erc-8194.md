## The name

**PGTR expands to Payment-Gated Transaction Relay.** It is not a trust registry, not a
reputation system, and not an identity standard. Any note that reads PGTR as "Portable
Agent Trust Registry" or similar is wrong; that misreading was current in our own notes
until 2026-09-20.

## What it does

A forwarder accepts an x402-style payment from a payer, checks it against an expected
amount and target, and calls the destination contract. The destination reads the
authenticated payer through `pgtrSender()` instead of `msg.sender`.

From the Abstract, verbatim:

> PGTR is **actor-agnostic**: the payer may be a human using a wallet app, an autonomous AI
> agent with a funded address, an IoT device, or any other token-holding entity. The protocol
> treats all principals identically — authorization is "I paid", not "I signed".

And on its relationship to ERC-2771, verbatim:

> ERC-2771 solves gas abstraction — the signer still needs a key and must produce an
> off-chain signature before the relay can act. PGTR solves **key abstraction** — any actor
> that controls tokens and can reach an HTTP endpoint can authorize on-chain actions without
> ever managing a private key.

## Interface

```solidity
interface IPGTRForwarder is IERC165 {
    function isPGTRForwarder() external view returns (bool);
    function pgtrSender() external view returns (address payer);
    function isTrustedForwarder(address addr) external view returns (bool);

    event PaymentGatedCall(
        address indexed payer,
        address indexed target,
        bytes4  indexed selector,
        uint256         paymentAmount
    );
}
```

`pgtrSender()` MUST revert outside an active forwarded call. Destination contracts MUST
check `isTrustedForwarder(msg.sender)` before reading it.

## Replay protection

Receipts are single-use. The canonical receipt hash, verbatim from the Specification:

```
keccak256(abi.encode(payer, amount, nonce, expiry, target, selector))
```

`nonce` MAY be random bytes32 or a monotonic counter. `expiry` is a Unix timestamp after
which the receipt MUST be rejected. The forwarder MUST store consumed receipt hashes and
reject duplicates.

## Relation to AAE

Both answer whether an agent may perform an action, and both bind the answer to a specific
action with an expiry and replay protection. PGTR's receipt hash carries `target` and
`selector`; AAE-02 §2.2.2 Action Binding does the same job. PGTR has `expiry`, AAE §2.4 has
`not_before` and `not_after`. PGTR consumes receipt hashes, AAE has `single_use` and §7.1.

Beyond that they diverge. PGTR covers one hop: one payer, one call, one destination. It has
no delegation chain, no constraint language and no verdicts. AAE-02 carries all three — §3
Delegation Chains, §2.5 Enforcement Constraint Language with predicate trace and recompute
determinism, §6 Verdicts and Ratification. PGTR is on-chain by construction; AAE is verified
off-chain against a document.

The sharpest difference sits in PGTR's own Rationale, under "Why payment receipt instead of
signed authorization?", verbatim:

> A signed authorization requires the principal to:
> 1. Have access to a private key.
> 2. Compute and transmit a valid signature before calling the relay.
>
> This requirement is incompatible with lightweight keyless agents operating in constrained
> environments.

That is a written argument against the AAE approach for keyless agents. Expect it back when
positioning AAE against PGTR.

**Prior art:** PGTR was filed 2026-03-10, `draft-kroehl-agentic-trust-aae-00` on 2026-05-21,
so PGTR is two months earlier. The claimed inventions do not overlap — PGTR claims relaying
without a key, AAE claims a machine-evaluable authorization envelope with constraints and a
chain. Treat PGTR as citable prior art for the opposing position, not as novelty-destroying.

**Interop:** the two stack rather than compete. PGTR answers who is calling, by letting the
destination read `pgtrSender()`. AAE answers what that caller may do. A destination contract
can require both.

## Where ERC-8195 uses it

ERC-8195 (Task Market Protocol, open PR [#1604](https://github.com/ethereum/ERCs/pull/1604),
`ERCS/erc-8195.md`, sha256 `05f0aafb3b8b975ac55ac84d13bc3cc29f317a8d6d7c5d8ef9fb0af6d66afedc`,
31891 bytes) routes worker actions through a trusted PGTR forwarder — the worker in
`claimTask`, `submitPitch` and `submitProof` is the authenticated `pgtrSender`. The
reference implementation carries `src/TaskMarketForwarder.sol`
(`daydreamsai/taskmarket-contracts`).

The dependency is also why #1604's build fails. The author wrote on 2026-03-17, verbatim:

> We have a failing build step which is caused by the fact that this ERC references ERC8194
> which is also currently being proposed so it can't resolve the link.

## Common attribution errors to avoid

- PGTR is not a trust or reputation registry. That role belongs to ERC-8004.
- There is no merged ERC-8194. Do not link `eips.ethereum.org`; it 404s.
- PGTR is not a profile of ERC-2771 — the draft says so explicitly.
- The x402 flavour PGTR builds on has **no ERC of its own**. Editor SamWilsn noted on
  2026-07-09, verbatim: *"I don't believe X402 has been defined in an ERC. You might want to
  either do that, or if the license permits, copy its specification into this document (or
  its assets directory)."*
