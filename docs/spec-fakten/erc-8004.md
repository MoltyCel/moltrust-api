# ERC-8004 — Bestand, Verknüpfung, Validator-Pfad

Stand 2026-09-18. Alle Kettenangaben sind live gegen Base Mainnet geprüft (a);
Angaben aus Fremddokumentation sind als solche gekennzeichnet (b).

## Position

MolTrust ist **Evidenzschicht auf** ERC-8004, keine konkurrierende Registry. Ein
Agent hat eine Identität mit zwei Namen: das `did:moltrust:`-Dokument und die
On-Chain-Registrierung. Beide Seiten nennen die jeweils andere, damit ein
Aufrufer von jeder Richtung aus ans Ziel kommt, ohne uns noch einmal zu fragen.

Das ist der Grund, warum bei der Registrierung **nichts neu geprägt** wird, wenn
bereits eine ERC-8004-ID existiert: verknüpft wird, nicht dupliziert.

## Bestand (a)

Chain `eip155:8453`, IdentityRegistry
`0x8004A169FB4a3325136EB29fA0ceB6D2e539a432`, Halter
`0x380238347e58435f40B4da1F1A045A271D5838F5`.

| tokenId | Registration-File | Name | did:moltrust | `registrations` |
|---|---|---|---|---|
| 21023 | `api.moltrust.ch/agents/did:web:api.moltrust.ch/erc8004` | MolTrust | nein (`did:web`) | nennt **33553** |
| 21351 | `api.moltrust.ch/agents/did:moltrust:455d06aa3d9d4fac/erc8004` | ERC8004-Test-Agent | ja | war leer |
| 21352 | `api.moltrust.ch/agents/did:moltrust:5709efa5e68b4da6/erc8004` | DualReg-Test-v2 | ja | 21352 |
| 33553 | `moltrust.ch/.well-known/erc8004.json` | MolTrust | nein | Feld fehlt |

`ownerOf` für alle vier bestätigt 0x3802. `balanceOf` = 4.

**Wie die vier gefunden wurden.** `tokenOfOwnerByIndex` revertet (kein
ERC721Enumerable), und der öffentliche Base-RPC deckelt `eth_getLogs` auf 2000
Blöcke — ein Voll-Scan über 51 Mio. Blöcke wäre 25.000 Anfragen. Blockscouts
`token-transfers`-Endpunkt liefert die vier Mints direkt. Zu beachten: Blockscouts
**NFT-Instanzliste** zeigte nur drei, während seine eigene Token-Bilanz 4 sagte —
der Index ist dort lückenhaft. Jede so gefundene ID wurde anschließend mit
`ownerOf` gegen die Kette geprüft, erst dann galt sie.

### Zwei Widersprüche im Bestand

1. **21023 nennt 33553.** Das Registration-File von Token 21023 führt unter
   `registrations` die agentId 33553 — die eines anderen Tokens. Beide gehören
   zur Plattform-Identität `did:web:api.moltrust.ch`, aber ein Leser, der 21023
   auflöst, bekommt eine Nummer, die nicht zu dem Token gehört, das er gerade in
   der Hand hält.
2. **33553 hat gar kein `registrations`.** Die statische Datei unter
   `.well-known/erc8004.json` nennt ihre eigene On-Chain-ID nicht.

Beides ist mit diesem Stand **nicht** behoben — siehe „Offen".

## Verknüpfung (B)

`alsoKnownAs` trägt die jeweils andere Identität:

- **DID-Dokument** (`/identity/resolve/{did}`): `alsoKnownAs: ["eip155:8453:<registry>:<tokenId>"]`
- **Registration-File** (`/agents/{did}/erc8004`): `alsoKnownAs: ["<did>", "eip155:8453:<registry>:<tokenId>"]`
- **`/identity/verify/{did}`**: Feld `erc8004` mit `agent_id`, `agent_registry`, `caip`

Emittiert wird nur, was tatsächlich hinterlegt ist. Ein DID-Dokument, das eine
On-Chain-Identität behauptet, die wir nicht belegen können, ist schlechter als
eines, das schweigt.

**Formhinweis.** W3C DID Core sieht für `alsoKnownAs` URIs vor. Die hier
verwendete CAIP-artige Kennung `eip155:8453:0x…:21352` ist keine URI im engen
Sinn. Sie ist bewusst so gewählt, weil ERC-8004 selbst in `agentRegistry` genau
dieses Format führt — ein Leser aus der 8004-Welt erkennt es unmittelbar. Wer
strikte URI-Konformität braucht, kann daraus `did:pkh` ableiten.

## Datenlücke, die dabei auffiel

Die leeren `registrations` waren **kein Code-Fehler**. `build_registration_file`
setzt das Feld korrekt, sobald ihm eine ID übergeben wird — die Tabelle kannte
sie nur nicht: von vier On-Chain-IDs war genau eine in `agents.erc8004_agent_id`
eingetragen. `migrations/2026-09-18_erc8004_backfill.sql` trägt 21351 nach.

Lehre für D: Die Verknüpfung muss beim Onboarding automatisch entstehen, sonst
läuft die Tabelle erneut auseinander.

## Reverse-Lookup (D)

`GET /resolve/erc8004/{agent_id}` gab bereits On-Chain-Daten und die verknüpfte
DID aus, aber **keinen** MolTrust-Score. Ergänzt um `moltrust_trust_score`
(score, grade, withheld, verify_url), ohne Key und ohne Kosten — das ist der
Sinn einer Evidenzschicht: wer nur die 8004-ID hat, soll fragen können.

Ein nicht berechenbarer Score wird als **abwesend** gemeldet, nicht als 0. Null
ist ein Urteil, Abwesenheit nicht.

## Validator-Pfad (C) — Spezifikation, kein Code

**Die ValidationRegistry ist nirgends deployt.** Geprüft:

- Das kuratierte Deployment-Verzeichnis (`erc-8004/erc-8004-contracts`) führt für
  **40+ Netze** ausschließlich IdentityRegistry und ReputationRegistry. Für die
  ValidationRegistry ist **keine einzige Adresse** genannt; die Spezifikation
  vermerkt sie als „still under active update and discussion with the TEE
  community" (b).
- On-Chain auf Base (a): IdentityRegistry `0x8004A169…a432` → 130 Byte Bytecode,
  ReputationRegistry `0x8004BAa1…9b63` → 130 Byte Bytecode. Beide deployt.
  Das Testnetz-Vanity-Muster `0x8004A818…` trägt auf Base keinen Code.

Damit gilt die Vorgabe „wenn nicht deployt: Adapter nur als Spec + Tests".

### Zielsignatur, sobald deployt

```solidity
validationRequest(address validator, uint256 agentId, string requestURI, bytes32 requestHash)
validationResponse(bytes32 requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag)
```

Abbildung der MolTrust-Verdicts auf `response` (uint8) und `tag`:

| Verdict | `response` | `tag` | `responseURI` |
|---|---|---|---|
| Trust-Score | 0–100, gerundet | `moltrust:score` | `/identity/badge/{did}` |
| Mandate-Check (MoltProof) | 100 konform, 0 verletzt | `moltrust:mandate` | `/moltproof/verdict/{did}` |
| Prediction-Verdict | 100 eingelöst, 0 verfehlt | `moltrust:prediction` | `/prediction/integrity/{market}` |

`responseHash` ist der SHA-256 des unter `responseURI` ausgelieferten Dokuments,
damit ein Leser die Antwort gegen das Dokument prüfen kann, statt uns zu glauben.

### Was vor dem Bauen entschieden sein muss

- **Feature-Flag** `ERC8004_VALIDATION_ENABLED`, Standard aus. Eine Registry, die
  noch in Revision ist, darf nicht stillschweigend Gas ausgeben.
- **Gas-Budget** aus 0x3802, mit Deckel je Tag. Ohne Deckel skaliert eine
  Verdict-Schleife direkt in die Wallet.
- **Signer menschengesteuert.** Der Schlüssel liegt laut `docs/WALLET_STATE.md`
  ohnehin unter Rotationsvorbehalt; automatisiertes Signieren ist eine eigene
  Freigabe.

### Heute schon möglich: ReputationRegistry

Die ReputationRegistry **ist** auf Base deployt, und
`app/erc8004.py:post_reputation_feedback` schreibt bereits dorthin. Wer
MolTrust-Evidenz on-chain sichtbar machen will, ohne auf die ValidationRegistry
zu warten, nutzt `giveFeedback(agentId, value, valueDecimals, tag1, tag2,
endpoint, feedbackURI, feedbackHash)` — dieselbe Hash-Bindung wie oben, nur auf
der Reputations- statt der Validierungsfläche. Das ist der kürzere Weg zum Ziel
„Evidenzschicht auf ERC-8004" und sollte vor dem Validator-Adapter entschieden
werden.

## Offen

- Die beiden Widersprüche im Bestand (21023 → 33553, 33553 ohne `registrations`).
  Beide betreffen die Plattform-Identität und die statische Datei im Web-Repo.
- Automatische Verknüpfung beim Onboarding (D, erste Hälfte).
- Validator-Adapter, sobald eine Adresse existiert.
